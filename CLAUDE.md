# Wholesome Girlies site: build rules

Static HTML on GitHub Pages, no framework. Preview with `python3 serve.py 8001` from the repo root (clean URLs work as on GitHub Pages). Before browser-testing, check which folder owns the port (`lsof -nP -iTCP:8001`). Stub `window.fetch` before clicking any checkout path, so a test never writes a row to the Checkout Intents sheet.

These rules apply to every page. `scripts/check-pages.py` enforces the machine-checkable ones and runs before every deploy. Run it before you commit:

```
python3 scripts/check-pages.py
```

**Hard rules** hold on every page today, and any violation fails. **Ratchet rules** have a known backlog that is frozen per page in `scripts/check-baseline.json`. A page fails only if it gets worse, or a new page breaks the rule. When you fix backlog pages, run `python3 scripts/check-pages.py --update-baseline` to lock in the lower counts. Never raise a baseline count to make a check pass.

The full plans live in the Obsidian vault under `Areas/Work/Wholesome Girlies/`: page templates in `01 - Website Architecture & Build Plan.md`, analytics in `Analytics Setup.md`, consent in `Consent Banner Build Scope.md`, checkout in `Checkout Intent Setup.md`, SEO in `SEO/02 - SEO Implementation Plan.md`, compliance in `_Resources/Compliance - Green and Red Tiering.md`, copy in `Content/_ChatGPT Project — WG Copy Engine/`, and sharing, print, games, and the app in `06 - Virality Plan.md` (section 8). When a rule changes, update it here, in the check script, and in the vault note that owns it.

## 1. Analytics and tracking

- GTM container `GTM-KW443M88` loads in `<head>` on every page, with its noscript iframe straight after `<body>`. GTM is the only tag loader: no gtag.js, no pixel init, no on-site InitiateCheckout or Purchase (Selar fires both). Lead fires only from `checkout-intent.js`; ViewContent only from GTM. Never run one event in two layers. *(hard)*
- Any page that loads `checkout-intent.js` starts `<head>` with the identity clean-up script (`window.__idq`), which strips personal details from the URL before any tag reads it. *(hard)*
- Selar links use `selar.com/<slug>?add_to_cart=1&email=&fullname=&mobile=` with the six product slugs. Diaspora pages add `currency=USD`; Nigerian pages never do. The `MOTHER` coupon appears only on the bundle upsell. *(hard, except the coupon placement)*
- Share links carry `?ref=wa|x|fb|th|li|ig|link`, and clicks push `share_click` with `share_channel`, `share_item`, and `share_surface`.
- GTM tags that wait for consent fire "Unlimited", never "Once per page" (container setting). GTM changes are staged by the service account and published by James. QA in a clean incognito window.

## 2. Consent and privacy

- `consent-defaults.js` loads in `<head>` after the identity script and before GTM. Every page loads `cookieconsent.css`, `wg-consent.css`, `cookieconsent.umd.js`, and `wg-consent.js`, and its footer carries the "Privacy choices" link (`data-cc="show-preferencesModal"`). *(hard)*
- Browser storage keys start with `wg_`, so the consent guard covers them. Tools compute on her device and store the segment, never raw health inputs on a server. *(hard)*
- A shared link never carries her answers, dates, or results.

## 3. SEO

- Every indexable page has a canonical equal to its own clean URL (no `.html`), the full Open Graph and Twitter card set with `og:url` equal to the canonical and an `og:image` that exists, the three favicon links, exactly one `<h1>`, alt text on every image, and `rel="noopener"` on new-tab links. *(hard)*
- `/go/` bridges, thank-you hubs, diaspora sales pages, and `404` carry `noindex, nofollow` and stay out of `sitemap.xml`. `robots.txt` has no Disallow lines, because a Disallow stops Google reading the noindex. *(hard)*
- `sitemap.xml` lists every indexable page by clean URL with a `<lastmod>`, and only `wg_release.py` (in `~/Documents/site-qa-tools/`) edits it, on release day. *(hard)*
- JSON-LD parses on every page. Guides: Article or MedicalWebPage, plus FAQPage and BreadcrumbList. Tools: SoftwareApplication and BreadcrumbList, and FAQPage *(ratchet)*. Nigerian sales pages: Product, FAQPage, BreadcrumbList. Home: Organization and WebSite. *(hard)*
- Every guide and tool is carded on its stage index, and every tool on `/tools/` too. Nothing ships unlinked. Every internal link and asset resolves. *(hard)*
- Meta descriptions run 155 characters or fewer *(ratchet)*; titles 50 to 60 characters, leading with the searched phrase.
- Tool trust layer: a Person author and a citation array in schema *(ratchet)*. Health pages that are sourced cite at least three recognised authorities and say plainly they are not yet reviewed by a clinician.
- **Every tool and guide has its own link preview card** at `/assets/img/og/<slug>.jpg?v=<version>`, used for both `og:image` and `twitter:image`, made by `scripts/make-og.js` *(hard)*. Tool cards show the title, a "Try it" pill and a live screenshot of the tool (checklists ticked, calculators filled with a sample date). Guide cards show a group chat: the hook from the Share Copy Bank winner (`scripts/og-hooks.json`, from `python3 scripts/share-bank.py --og-json`) as the message, the guide as the shared link. Sensitive guides get a single heart reaction. Every other indexable page uses `/assets/img/og/default.jpg?v=<version>` (the home headline beside the five stages as stickers); the Organization logo in schema is `icon-512.png`, never a card. Each run also saves a 1080×1350 (4:5) feed post of every card to `~/Downloads/Wholesome Girlies/Social Posts/<stage>/`, so a new tool or guide gets its post the same run it gets its card; `--square-only` remakes just the posts. When a card changes, re-render it and bump `OG_VERSION` and every meta tag, so WhatsApp, X and Facebook fetch the new image. The approved cast replaces this art next (plan in the vault's `Content/WG Cast/00 - WG Cast Bible.md`, Website images).
- **Result cards** *(hard)*: every quiz or checker result type is listed in `scripts/results.json` with a cast scene in `assets/img/cast/results/`. `scripts/make-result-cards.js` renders its 1200×630 link preview and 1080×1920 Status card into `assets/img/results/<tool>/`, and `scripts/make-result-pages.py` writes the noindex result page at `/<stage>/tools/<tool>/result/<type>` plus `assets/js/wg-result.js`. The tool calls `wgShowResult(type)` after scoring and carries `<div id="wg-result-share" hidden>` in its result panel. A result link never carries her answers. Results that show a safety route (control, threats, force) never get a share row. Words go in the layout, never in the AI art.
- **Brand profiles are the same five everywhere** *(hard)*: Facebook `/wholesomegirlies`, Instagram `@wholesomegirlieshq`, TikTok `@wholesomegirlies`, X `@wgirlieshq`, LinkedIn `/company/wholesomegirlies`. Every footer social row links all five, every page with an X card carries `<meta name="twitter:site" content="@wgirlieshq">`, and the home page Organization `sameAs` lists all five. The X share button adds `via=wgirlieshq`. A new profile (YouTube when it launches) goes into all three places and the check's `PROFILES` list together. The registry is the vault's `05 - Accounts & Platform IDs.md`.
- `llms.txt` URLs all resolve *(hard)*. No hreflang *(hard)*. Run `/seo-audit` and `/ai-seo` after any batch of page changes.

## 4. Page structure

- **The homepage** follows the order signed off in the vault's `07 - User Journeys, Navigation & Wireframes.md` (G1, G2): the hero with the four stage guides, "Wherever you are, start here", six tools (one per motherhood stage plus the two newest games, until ad traffic shows the most used), "Questions women ask" with three guides, the programs block, the app card, and why trust us. When the browser holds a program home, `wg-program-home.js` shows a "Your program" card under the header with "Up next" and "Continue reading" where the program has a reader.
- Sales pages and `/go/` bridges carry no site navigation. *(hard)* Program homes (the thank-you pages) carry only the slim header: the brand, Tools, and "My programs" when her phone holds two or more programs.
- Sales page sections alternate after the hero: plain, then `stage-band` (tinted), then plain, and so on. When you add or remove a section, re-alternate the rest of the page so two tinted or two plain sections never touch. *(judgement)*
- **Images.** Stage hubs and guides use cast illustrations from `assets/img/cast/`: 16:9 JPG at 1100×618, under 200 KB, `width="1100" height="618"`, alt text that starts "Illustration of" and never presents a cast member as a real woman. No cast character on loss pages, the mental-health check-ins, or the postpartum warning signs guide; those get a still life with no person. Sales pages carry no scene or cast images (the bundle mockup is the only picture) and no separate mechanism or differentiator section, and no "Who guides you" or where-the-facts-come-from credentials section (the safety note and the FAQ carry the doctor line), so they stay lean. `scripts/check-pages.py` fails a program page with a "Who guides you" eyebrow. Each stage has a guide, a waist-up cutout in `assets/img/cast/guides/` (relationships Tolu, fertility Amaka, pregnancy Zainab, postpartum and parenting Funmi): `scripts/build-stage-look.py` puts her at the right of the header on every tool page and stage hub, the homepage hero shows four of them, and the program homes and the app greeting sit beside her. The same exclusions hold: no guide on loss pages, the mental-health check-ins, the warning signs guide, written guides or shared result pages *(hard)*. New cast images are made from the approved masters in the vault (`Content/WG Cast/Masters/`), with GPT Image, attaching only the sheets of the people in the scene.
- `/go/` bridges show no price, never link to Selar, link only to their own market's sales page, and carry the legal links row. Ads point only at `/go/`. *(hard)*
- Nigerian sales pages show naira only and load `geo-redirect.js`; diaspora pages show dollars on the page. Every sales page has `id="join"` and loads `checkout-intent.js`. *(hard)*
- Thank-you hubs write their `wg_<stage>_home` member flag, never gate what she paid for, and carry the share block. *(hard)*
- **Program homes** (`programs/<slug>/thank-you`) are her daily home, so they carry no tool videos *(hard)*. `scripts/build-program-homes.py` writes each page's header and main from `assets/data/program-homes.json`, in the order signed off in the vault's `07 - User Journeys, Navigation & Wireframes.md`: who it is for, reading (the reader where one is built, otherwise the toolkit PDF), Get the app (browser only), community (motherhood only), her tools as a list with "Saved" marks, help and safety with the helpline, the next program, and pass it on. Never edit between `<!-- program-home:start -->` and `<!-- program-home:end -->`; edit the data file and rerun the script. A new tool goes into the file's `tools` and its stage list, and a new program into `homes` *(hard: the check fails a tool or program home missing from the file, and a stale page)*.
- **Every resource page** (tool, guide, checklist, template, game, quiz) carries a share line in `<meta name="wg:share">`, `wg-rail.css`, and `wg-article.js` loaded after `member-cta.js`. Together they build the sticky contents panel when the page has two or more `<h2>` headings, and the share icons on every page: in the contents panel, in a row straight under the tool on tools (never inside the written guide) or under the byline on guides, and in an end row above the program card. A tool with no written guide under it gets only the row under the tool. It also carries the stage program card (`.program-cta`), which `member-cta.js` swaps for "Go to your [program] home" for buyers. *(hard)*
- **Every printable tool** loads `wg-print.css` with `media="print"` and `wg-print.js`, has a `data-wg-print` button labelled "Print or save as PDF", and has a QR code made by `scripts/make-print-qr.js`. The printout shows only the tool, its disclaimer, and its safety box. *(hard)*

## 5. Share copy

- `assets/js/wg-share.js` renders the icon row (WhatsApp, X, Facebook, Threads, LinkedIn, Instagram, copy link) from a `<div class="wg-share">` with `data-share-path`, `data-share-text`, and optional `data-share-size="sm"` and `data-share-align="center"`. Thank-you hub links point at the public program page, never the hub. *(hard)*
- The share line is written in the sharer's voice and must make sense to a stranger who sees it cold on WhatsApp or X. It never reveals her own stage, condition, or purchase. It stays under 250 characters so it fits X with the link (X counts any link as 23). *(hard: present, under 250)*
- `<meta name="wg:share-label">` sets a softer prompt on loss pages and private trackers.

## 6. Compliance

- Green tier only. Every health tool and guide carries "educational, not medical advice" and a when-to-see-a-doctor or safety block *(ratchet)*. Mental-health content routes to real care and MANI on 0809 111 6264.
- No review claim ("medically reviewed by", "reviewed by professionals") until a named clinician has signed. The credibility ceiling is "research and data-backed", or "sourced, not yet reviewed by a clinician". *(hard)*
- Never imply we know her condition. No diagnose, treat, or cure claims. No outcome or timeline promises: no conception promise, no marriage guarantee, no birth or body promise. *(judgement)*
- Banned trigger phrases: "get pregnant fast", "boost fertility", "bounce back", "get your body back", "sleep through the night", "make him marry you", "make him choose you". Guides may quote a searched question in order to answer it; share lines and every other page may not. *(hard)*
- Honest urgency only: no countdowns, fake scarcity, or guaranteed results. *(hard)* Testimonials are verbatim from the proof file with first name and initial, stage, and city. Sales pages with testimonials carry a results-vary line *(ratchet)*. Only the 6-Week Postpartum Reset ("300+ first-time mums") and the Wife Material Blueprint ("300+ women") may cite a number.

## 7. Brand and copy

- Write "Wholesome Girlies" in full in all copy, including text a script builds on the page, never "WG": readers do not know the short name yet. *(hard)*
- Say "assistant", never "bot". The public price label is "early-bird", never "founding". Program names are locked: The Trying-to-Conceive Blueprint, The First Pregnancy Plan, The 6-Week Postpartum Reset, The First Baby Playbook, The Wife Material Blueprint, The Complete Motherhood Journey. *(hard)*
- Never call the tools or content "free" in customer-facing copy. *(ratchet)*
- No em or en dashes in copy, including `<title>` and meta descriptions; use commas and periods. *(ratchet)* Plain language, short sentences, medical terms explained where they appear, the collective "we", no hype, fear, or pressure. James's writing rules (`~/CLAUDE.md`, Writing Style Guidelines) apply to all copy.
- Never use "honest", "calm" or "gentle" (or honestly, calmly, calmer, gently, gentler) as filler. Say the specific thing: name what the milestones, answers or plan actually hold, and use the Nigerian detail where it fits. Keep one only where it is the literal, precise word (a physical instruction like "press gently"), at most once per page, and never swap in "kind", "soft", "real" or "clear". `scripts/check-pages.py` warns on any page that uses them more than once. *(judgement)*
- Program sales page heroes (eyebrow, h1, lead, price button) are approved copy. Copy and voice passes leave them alone unless James names them, and keep the allowed proof claims, including the Wife Material "300+ Nigerian women ... in less than 12 months" headline. *(judgement)*
- Colour tokens kept their old names when the palette changed: `--terracotta` is olive (the primary colour, used for good, safe and green-flag meanings) and `--sage` is rust (warnings, safety boxes, red-flag meanings). Choose by the colour, never the name. A tool that colours answers green and red uses `--terracotta` for green and `--sage` for red.
- **The sticker look** (in `styles.css`, the program home and reader styles, and the app tab bar in `wg-app.js`): cards, tools, results, buttons and icon chips carry a 2px ink outline (`--ink`) and an offset ink shadow (`--sticker`), in the cast scene colours `--rust`, `--olive`, `--mustard`, `--denim` and `--peach`, each with a tint (`--rust-t` and so on). Each stage has one colour: relationships rust, fertility olive, pregnancy mustard, postpartum peach, parenting denim. A page takes its stage from `<html data-stage>`, which `scripts/build-stage-look.py` stamps from the address (programs and bridges take their program's stage, the Complete Motherhood Journey takes parenting), and `--s`, `--st` and `--s-on` give the stage colour, its tint and the text that sits on it. Mustard and peach are light, so text and icons on them are ink, never white. Run the script after adding pages; the page check fails a stale page *(hard)*.
- James's own face never appears; women's faces are fine. Never present a stock or AI person as a real named woman. The founder stays private; Cynthia Obinatu is the named author and editor.

## 9. Operations

- Inline scripts must parse *(hard)*: the page check runs each one through Node, because one syntax error stops a whole tool working.
- Assets load with `?v=YYYYMMDD<letter>`. When you change an asset, bump its version in every file that references it, including the `wg-share.js` reference inside `wg-article.js`. Every `/assets/` script loads with a version *(ratchet: `member-cta.js`, `geo-redirect.js`, and `petals.js` load without one today)*. Mixed versions fail. *(hard)*
- **Every new tool, game or quiz gets a tool short** *(hard on James's machine)*. In the same session the tool is built, add its row to the vault's `Content/AI Video/01 - Video Roadmap.md` under its program (or the stage's program), assign it a style in `04 - Tool Short Styles.md`, and write its brief from `_Video Brief Template.md` under `Content/AI Video/<Program>/` as the program's next number (tool shorts come first in the program's folder, so renumber the UGC and dialogue briefs that follow, and the rendered files under `~/Downloads/Wholesome Girlies/Videos/Tool Shorts/<Program>/`) with `destination: /<stage>/tools/<slug>` and the tool's real output for the inputs shown. The page check fails any tool page with no brief whose `destination` matches; it skips this check where the vault is absent (the GitHub runner).
- **Tool reels.** Each tool short plays as a tap-to-play phone clip on the sales pages (under the price card). Program homes and the app home `/app/` show no reels: they list the tools instead (sections 4 and 10). The pipeline: ship the tool, write its brief, render the short, run `node scripts/publish-to-site.mjs <tool-slug>` in `~/Documents/site-motion-kit` (cuts the loop and poster into `assets/video/tool-shorts/` and `assets/img/tool-shorts/`, writes the tool's entry in `assets/data/tool-shorts.json` with a fresh `tool_fingerprint`, then runs `scripts/build-tool-reels.py`), and the reels update on every page the entry lists. Never edit the HTML between `<!-- tool-reel:start -->` and `<!-- tool-reel:end -->`; edit the manifest and rerun the generator. The reel CSS and JS are `wg-tool-reel.css` and `wg-tool-reel.js`. Clips load only on tap, one plays at a time, there is no autoplay, and private tools (they keep her answers on her phone) carry "Private. Stays on your phone." Program hero copy and the sales page order are untouched. `scripts/check-pages.py` guards it *(hard)*: every manifest tool appears in the reel of every sales page it belongs to, each reel matches what the generator would write, a tool page whose fingerprint (its `tool-app` markup plus its inline script, never the share rows, schema or head) differs from the manifest fails with "tool changed since its short was filmed", and a brief with no manifest entry only warns while the short is being rendered. If a tool changes but what the short shows does not, run `publish-to-site.mjs <slug> --refresh-fingerprint`. A new sales page needs the two marker comments placed once by hand.
- Deploy is a push to `main`: GitHub Actions runs this check, then publishes to Pages. Check the current branch and unpushed commits first, because other sessions leave repos on their own branches. Cloudflare is DNS-only.
- Secrets never go in the repo or the vault. Everything in this repo is publicly readable on the site.

## 10. The app (website and app ship together)

The installed app is the website. "Girlies" on her home screen opens `/app/` from `manifest.webmanifest`, and `sw.js` saves pages and files so the tools work without data. There is no separate app build and no store: one push to `main` ships the website and the app together. These rules keep the two from drifting apart.

- **How an update reaches her.** Pages load from the network first, so a pushed page shows in the app the next time she opens it online. Offline she sees the copy from her last visit. Files in `/assets/` load from the cache first, so a changed asset reaches the app only through its `?v=` bump (section 9). An asset changed without a bump stays old in the app indefinitely. *(hard: mixed versions fail)*
- **Every page carries the app tags** *(hard)*: the manifest link, `theme-color`, `apple-mobile-web-app-title` ("Girlies"), `wg-app.js`, and "Get the app" in the footer Explore list (never in the menu). After adding pages, run `python3 scripts/add-app-tags.py`, then `python3 scripts/build-tool-reels.py`, which keeps the reel script last before `</body>`. When `wg-app.js` changes, bump `APP_JS_VERSION` in `add-app-tags.py` and run it again.
- **`sw.js`.** Bump `VERSION` whenever `sw.js` changes (its logic, `CORE`, `SKIP` or `LATER`). The new worker takes over on her next open and deletes the old cache. Ad bridges, sales pages and video clips never get cached. Reel posters are cached when she scrolls to them, never on install, so installing costs little data.
- **A new tool** works offline only if `/tools/` links it, because the worker saves every tool linked from `/tools/` on install (section 3 already requires the link). If it saves entries, add its storage key to `APP_TOOLS` in `app/index.html` so "Your saved tools" shows it *(hard)*. If it is sensitive (loss, mental health, warning signs), add its path to `QUIET` in `wg-app.js` so no install offer appears on it. Never rename a storage key without moving her old entries across, because the site and the app lose them together.
- **A new game or quiz** replaces the older card under "Newest games" on `/app/` (keep two), in the same push. The app home carries no tool videos *(hard: the check fails a reel on `/app/`)*.
- **The manifest** (name, icons, colours, `start_url`) changes only with James's go. Android Chrome checks for a changed manifest when she opens the app, at most once a day. iPhone keeps the old name and icon until she adds the app again.
- **The install offers.** A card ("Get the Girlies app" on a phone, "Get Girlies on your phone" on a computer) sits under game and tool results, on thank-you hubs and on the homepage after the programs block (its section stays hidden when no card is offered). A bottom bar appears on phones after she saves a tool entry, at most once a visit and 14 days quiet after she closes it. Neither appears inside the installed app, on sales pages, on `/go/` bridges or on the `QUIET` pages. The `app_*` events go to the dataLayer without her entries. Tag Manager tags for them are staged by the service account and published by James.
- **The steps sheet matches her browser**, because only Android Chrome has an install button a page can trigger. iPhone Safari gets the iOS 26 steps (••• → Share → View More → Add to Home Screen) with the recording. iPhone Chrome gets Share at the top right, and Edge and Firefox get their menu. In-app browsers (Instagram, TikTok, WhatsApp) are told to open the page in their browser first. Android gets the install prompt or the menu steps, and a computer gets a QR code that opens `/app/` on her phone. Check every variant from a Mac by adding `?preview=iphone`, `iphone-chrome`, `android`, `in-app`, `computer` or `installed` (the app as it opens from an iPhone home screen) to any page. When Apple or Google move the menu items, rewrite these steps and re-record the clip.
- **The install recording** (`assets/video/app/install-iphone-safari.mp4` and its webp poster) is James's own screen recording, put through `scripts/make-install-clip.sh`. Its blur bands hide the status bar, the contacts in the share sheet and the other apps on his home screen, and keep only the Girlies icon sharp. A new recording gets the same blur pass before it ships *(hard: no personal data on screen)*, plus a `?v=` bump.
- **`/app/` changes with who is looking.** The install card shows the recording in iPhone Safari, the QR code on a computer (`assets/img/qr/app.svg`, made by `scripts/make-app-qr.swift`, which also checks the code scans) and the phone mockup on every other phone. The mockup is a capture of a real tool made by `scripts/make-app-mockup.js`: remake it when that tool's look changes, and bump its `?v=`. Inside the installed app the install card is gone. The first open says "You are set" and later opens say "Welcome back". A buyer sees her program first (a reading card with "Up next" where the program has a reader, otherwise a card that opens her program home), then "Your tools" (the tools she has saved, then her program's, with "Saved" marks), then "Newest games", and no tool videos. Anyone else who has saved entries sees "Pick up where you left off", "More for your stage" (the stage she uses most) and that stage's program (`APP_PROGRAMS` in `app/index.html`). With nothing saved she sees the homepage's "Wherever you are, start here" stage cards with the same emojis and lines, each linking straight to that stage's program. The tool names, lines and each program's stages and reader come from `APP_DATA`, which `scripts/build-program-homes.py` writes from `assets/data/program-homes.json` *(hard: the check fails stale data)*. A new program gets a line in `APP_PROGRAMS` and its card's link. Backup and restore sit under "Back up or restore your entries".
- **Inside the installed app the footer is two small lines** (`appFooter()` in `wg-app.js`): "Educational, not medical advice", Disclaimer, Privacy, Health data and Privacy choices. The page source keeps the full website footer, which the page check reads; never drop Privacy choices from the app line, because consent must be changeable at any time.
- **Before a push that touches the app**, with the site on :8001, run `python3 scripts/check-pages.py`, `NODE_PATH=/tmp/wgog/node_modules node scripts/test-app.js` (service worker, app home, backup code, install offers and where they stay quiet) and `node scripts/test-app-offline.js` (a real dropped connection). The local `serve.py` answers byte-range requests, without which Safari will not play the recording. Then check one iPhone and one Android phone on the live site after the deploy.
